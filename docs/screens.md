# 画面フロー（MVP）

> 記録は「その日のトレーニングを開始 → 種目ごとに完結させて積み上げる」流れ。ホーム画面はカレンダー表示から始め、棒グラフ・キャラ成長は後のフェーズで足していく。
> 詳細な検討経緯は企画メモ（Artifact）のセクション05を参照。

## 画面一覧

| 画面 | 役割 |
|---|---|
| ① ログイン／新規登録 | email・パスワード・表示名 |
| ② ホーム | カレンダー表示（記録日をマーク、選択で詳細）。棒グラフ・キャラ成長は後のフェーズで追加 |
| ③ 記録作成 | その日のworkoutを開始。種目を1つずつ登録して積み上げる本体画面 |
| ④ 種目選択 | 部位ごとにセクション分けされた1画面。各セクション上位5件表示＋開閉トグルで全件表示 |
| ⑤ ルーティン一覧・編集 | よく使うメニューをテンプレート登録。0件なら③から誘導される |
| ⑥ 記録詳細 | 過去1回分のworkout＋workout_setsを見返す |
| ⑦ 種目追加 | 部位（選択式・遷移元がデフォルト）＋種目名（自由記入）の共通画面 |

## 記録するときの一連の流れ

```
② ホーム
  └─「＋今日の記録を始める」
       └─ ③ 記録作成（workoutを開始）
            ├─ ルーティンから選ぶ → ⑤の登録済みメニューから種目一式が並ぶ
            │    （⑤が0件なら → ⑤ルーティン新規登録へ誘導）
            ├─ 個別に種目を足す → ④ 種目選択
            │    部位（胸/背中/脚/肩/腕/お尻/腹筋）ごとにセクション分けされた1画面
            │    各セクションは上位5件のみ表示（矢印タップで全件表示⇄折りたたみ）
            │    　└ 表示順：自分の使用回数が多い順（履歴が無ければ運営の定番順）
            │    種目を選択 → ③へ戻る
            │    見つからなければ「＋種目を追加」→ ⑦ 種目追加画面
            │         部位は遷移元のセクションがデフォルト選択（変更可）、種目名は自由記入
            │         → 登録した種目は同じグループの仲間にも見えるようになる
            ├─ 選んだ種目についてセットを複数入力（重量・回数）→「登録」
            │    → その種目分のworkout_setsを保存 → ③へ戻る（登録済み種目が積み上がる）
            └─ 続けて次の種目を追加、または「今日の記録を完了」→ ② ホームへ
```

## 設計方針メモ

- **記録は種目ごとに区切って都度保存**。1日分をまとめて最後に一括保存するのではなく、種目を1つ終えるたびにworkout_setsが確定していく（ジムでの実際の動きに合わせた設計）
- **最初からレスポンシブで実装**。PC先行で作って後からスマホ対応、ではなく、作り込み（アニメーション等）は最小限にしつつ最初からスマホでも使える形にする。主な利用シーンがジムでのスマホ操作であるため
- **表示順ロジック**：自分の使用回数 DESC → default_sort_order ASC → 名前順（詳細はschema.md参照）
- **筋肉イラスト可視化（Phase3）**：④種目選択の部位セクションを土台に、react-native-body-highlighterのSVGを使って段階的に拡張予定（詳細はschema.md参照）

  - **再検討のタイミング**：セット数・重量の桁数が実際に増える場面（セットを10本以上、重量を
    3桁以上記録するケースなど）で改めて見た目を確認したタイミング
- ~~③記録作成の入口を「今日」固定にするか、カレンダーで選択した過去日からも記録作成を開始できるように
  するか~~ → Issue10では「今日」固定として実装（②ホームの「＋今日の記録を始める」のみが入口）。
  過去日からの記録作成対応は引き続き未着手
- セット記録画面：同じ種目で複数セットを連続して行う際、1セットごとに「記録」ボタンを押す方式に
  している（Issue10実装時点）。ジムで実際に使う場面では、複数セット分をまとめて入力してから
  一括登録できた方が手間が少ない可能性があるため、入力方式の改善を今後の課題として検討する
  - **再検討のタイミング**：実際に使ってみて「1セットごとの記録が手間」という体感が積み重なった
    タイミング。それまでは動作の分かりやすさ（都度保存され消えない）を優先し、無理に先取りしない
- ②ホームの「＋今日の記録を始める」ボタンの文言を「＋今日の記録をつける」に変更する案（Issue10の
  レビューで出た指摘）。優先度が低いため見送り、まとめて見直すタイミングで対応する
- ②ホームのカレンダーで日付を選択したときの挙動：現状は選択してもその日の記録作成には連動しない
  （③の入口は「＋今日の記録を始める」のみ、常に今日固定）。カレンダーで過去日を選ぶとその日の記録
  作成画面が開き、今日の日付を選ぶと今日の記録作成画面が開く、という「日付選択がそのまま記録作成の
  トリガーになる」設計への変更を今後検討する
  - Issue10実装時点では、③の画面設計自体が「今日固定」を前提に作られている（`useWorkoutSession`が
    performedAtを引数に取る形にはなっているため、日付を渡す口自体は用意済み）。過去日対応をやる場合は
    ③の入口設計・ホーム側のUI（カレンダー選択→遷移の導線）を合わせて見直す必要があり、範囲が
    ①つのIssueとしてはやや大きいため、Issue10のスコープからは切り離した
  - **再検討のタイミング**：Issue10がひと段落し、次にどのIssueへ進むか検討するタイミング
- ③記録作成にメモ入力欄を追加する案（元のIssue10には無かったが、実装中の質問「メモは書ける？」から
  出たアイデア）。`workouts.memo`カラム・`PATCH /workouts/:id`のAPI自体はIssue6時点で用意済みなので、
  フロント側を繋ぐだけで実現できる。動く実装は`feat/workout-recording`ブランチに残っている（メモを
  空文字列で送るとクリアできる、という仕様も含む）ので、着手時はそちらを参考にできる
  - **再検討のタイミング**：③のスコープを広げる次のIssueを検討するとき
- ③「今日の記録を完了」を押したときに確認を挟む案（元のIssue10には無かったが、レビューで「押しても
  反応が無いように見える」という指摘から検討したアイデア）。`feat/workout-recording`ブランチでは
  `window.confirm()`を使ったところ、ブラウザが「このページに追加のダイアログを表示させない」を
  自動的に有効化すると以後`confirm()`が常に`false`を返し、ボタンが完全に無反応に見える不具合を
  実機で確認した。**今後この手の確認UIを作るときは`window.confirm()`を避け、画面内の2段階確認
  （キャンセル／実行ボタン）にする**、という学びだけ残しておく（実装例は同ブランチ参照）
- ③種目を1つも追加していない状態で「今日の記録を完了」を無効化するガードの要否。データの意味的には
  空のworkoutが作られてしまう点が気になるが、元のIssue10の完了条件には含まれていないため今回は判断を
  保留する
  - **再検討のタイミング**：空のworkoutが実際に増えて困る場面が出たとき
- ④「もっと見る」をアイコン付きの開閉ボタンにする等の見た目の装飾。優先度が低いため見送り、まとめて
  見た目を整えるタイミングで対応する
- ③のセット記録画面から④種目選択へ直接戻れるリンクを追加する案。「この種目の入力を終える」→
  「＋種目を追加」の2手順で代替可能なため優先度は低いが、動線として欲しくなったら追加する
