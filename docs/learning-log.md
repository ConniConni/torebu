# 学習ログ

技術の勉強を兼ねているので、実装しながら気づいたこと・詰まったこと・理解できたことをここに書き残す。
「なんとなく動いた」で終わらせず、**なぜそう実装したかを自分の言葉で書く**のが目的。

書き方の目安：

- 完璧な文章でなくてよい。箇条書き・殴り書きでOK
- 「わからなかったこと」もそのまま書く（後で見返して成長がわかる）
- 日付ごとに追記していく（新しい方を上に）

## 効果的に書くためのコツ

**タイミング**

- そのセッション／作業がひと段落したタイミングで、**記憶が新しいうちに**書く。翌日以降にまとめて書こうとすると、細部が抜けて「なんとなく理解した気がする」で終わりやすい
- 1 Issue = 1セッションの区切りと相性がいいので、PRを出す前後に書くのを習慣にする

**書き方**

- **何も見ずに、自分の言葉で説明できるか試してから書く**（検索や会話ログを見返すのは、書けなくて詰まってから）。これが一番の理解度チェックになる
- 「なぜそれを選んだか」を書く。「Vitestを使った」ではなく「NuxtがViteベースだからVitestが噛み合う、と理解した」のように理由まで書く
- わからなかったことは誤魔化さずそのまま書く。「〇〇がなぜそうなるのか分からなかった」は次に潰すべき課題のリストになる

**書いた後**

- ある程度溜まったら`/review`で復習問題を出してもらい、実際に説明できるか確認する
- 何度も引っかかる概念があれば、次のセッションの最初に「〇〇についてもう一度説明して」と聞き直す

### 用語集ではなく「使いどころ」が足りなかったことについて

- §0の用語17語には印が1つも付かなかったのに、「意味は分かるが、それらをどう使うかが分かっていない」という感想が出た。**言葉を知っていること**と**その言葉が指すものを使えること**は何がどう違うのか、自分の言葉で説明できるか
  - 知っている＝その言葉が何を指すか答えられる。使える＝どういう場面でそれを持ち出すべきか判断できる。自分に無かったのは後者。辞書は持っているが「いつ引くか」の索引が無い状態
- 「編集するのはPATCHだけど対象を選ぶときにGETがいる」という例を自分で挙げた。この「AをするにはBが必要」という結びつきは、用語の一覧を眺めることでは身につかなかった。ではどうすれば身についたと思うか
  - 編集画面を1つ、APIから画面まで自分で通しで作ること。結びつきは定義からは出てこず、場面を1回通ったときに「GETが無いと編集対象が決まらない」と体で分かる形で出てくる
  - 用語集は「部品カタログ」であって「組み立て説明書」ではない。カタログを何度読んでも組み立てられるようにはならない

### 認証と認可の違いについて

- 流れ①の2番目に「ミドルウェアで認可状況を確認」と書いたが、`POST /auth/login`に認可の確認は入らない。なぜ入らないのか、ログインという処理の性質から説明できるか
  - 認可は「この人にこれをする権利があるか」の判断なので、**その人が誰かが確定していないと判断しようがない**。ログインはまさに「誰か」を確定させる処理そのものなので、その入口で認可を確認することはできない
- ではログイン時に通る`sessionMiddleware`は何をしているのか。`requireAuth`はどのタイミングから効き始めるのか
  - `sessionMiddleware`はCookieがあればセッションを復元する係。初回ログインではまだCookieが無いので、実際には何も復元しない（通過するだけ）
  - `requireAuth`が効くのは、ログイン成功でCookieを受け取った**後**のリクエストから。流れ①でいえば9番の`GET /auth/me`が最初
- 「認証（authentication）」と「認可（authorization）」を、このアプリの具体的な処理を例に区別して説明できるか
  - 認証＝あなたは誰か。`bcrypt.compare`でパスワードを照合している部分
  - 認可＝あなたにその権利があるか。`findOwnWorkout`で「そのworkoutはあなたのものか」を確認している部分
  - 順番が決まっている。認証が先、認可が後。逆はあり得ない

### TypeScriptの型システムについて

- **TypeScriptは「静的解析」＝コードを実行せずに読むだけで型をチェックする道具**。実行時に何が起きるか（例えば「このミドルウェアを通ったら、この変数は絶対存在する」）までは、TypeScript自身は分からない。あるチェック（if文など）の結果を、別の関数に引き継いで伝える仕組みは基本的に無い。だから今回、`requireAuth`ミドルウェアで「ログイン済みかどうか」を確認した後でも、その次の処理（ルートハンドラ）の中で`req.session.userId`を使うときは、TypeScriptは「もしかしたら無いかもしれない（`undefined`）」という扱いのままになる。人間には「絶対あるはず」と分かっていても、コンパイラには`!`（非nullアサーション。「これはnullやundefinedではないと保証する」という意味の記号）で明示的に伝える必要があった
- **ライブラリが提供する型は、ライブラリ側の設計判断を反映している**。`express-session`というライブラリでは、`req.session`にどんなデータを入れるかはアプリ側で自由に決められるので、`declare module`という書き方でこちらから型を追加している（[session.ts:5-9](backend/src/session.ts:5)）。ただし実際にはその型全体が`Partial<T>`（Tの全プロパティを「あってもなくてもいい」扱いにするTypeScriptの組み込み機能）で包まれた形で使われる。「未ログインの人はセッションに何も入っていない」という現実を、ライブラリが型でそのまま表現している、というのが今回の発見
- **Express（Webサーバーのフレームワーク）は、ルートのパス文字列（`/workouts/:id`など）から、そのパラメータの型（`{id: string}`）を自動で推論してくれる賢い仕組みを持っている**。ただし、これは関数呼び出し全体（今回でいうと、ルート定義に一緒に渡すミドルウェアも含めて）が矛盾なく型が決まる場合だけ機能する。汎用的に書かれた`requireAuth`のようなミドルウェア（パラメータの型を specify していない）を一緒に渡すと、TypeScriptは「全体で矛盾のない、一番ゆるい型」を選んでしまい、`req.params.id`が`string`ではなく`string | string[]`という、より曖昧な型になってしまった。対処として`as string`（「これはstring型として扱ってよい」と伝えるキャスト）を使った

### Webアプリ・API設計について

- **ソフトデリート**とは、行を本当には消さず「削除済みフラグ（`deletedAt`に日時を入れる）」を立てるだけの削除方式。物理的にデータが残るので、それに紐づく別のデータ（今後実装予定のリアクション・コメント等）を保持できる。**注意点は、"検索する"あらゆる場所で「削除済みは除外する」条件（`deletedAt: null`）を書き忘れないこと**。書き忘れると「削除したはずなのに一覧に出てくる」「削除したはずなのに編集できる」という不具合になる。今回は「新規作成（POST）」には不要で、「既存のデータを探しに行く処理（一覧・詳細取得・編集・削除・関連データの追加）」全部に必要、という区別が重要だった
- **認可（自分のデータかどうかのチェック）とIDOR対策**：IDOR（Insecure Direct Object Reference）とは、URLやリクエストの中のID（例：`/workouts/xxxx`の`xxxx`部分）を誰でも自由に指定できることを悪用し、他人のデータにアクセスできてしまう脆弱性のこと。対策の基本は「操作対象を必ず`ログイン中のユーザーID`で絞り込んでから探す」こと。加えて今回は、**他人のデータであることが分かる`403`（禁止）ではなく`404`（存在しない）を返す**ようにした。理由は、403だと「そのIDのデータは存在する（が権限がない）」ことが分かってしまい、存在自体を教えてしまうから
- **RESTfulな設計での「親子関係のあるリソース」の表現方法**：`workout_sets`は必ず`workouts`に紐づくデータなので、URLも`/workouts/:id/sets/:setId`のように親のIDをパスに含める形にした。こうすることで「そのセットが、指定した`workoutId`に本当に属しているか」を毎回一緒に確認でき、認可チェックがシンプルになる（もし`/sets/:setId`のように独立させていたら、別途「このsetは今ログイン中のユーザーの持ち物か」を確認するために、必ず親を辿る処理が必要になっていた）

### テストについて

- **Vitest（テストツール）は、複数のテストファイルを"同時に"（並列に）実行することがある**。1ファイルずつ順番に実行しているわけではない。ただし、繋ぎに行くDB（PostgreSQL）は1個の実体を全ファイルで共有している。だから、あるテストファイルの後片付け処理（`afterEach`）が「テーブルの中身を全部消す」というような**自分専用でない範囲まで巻き込む書き方**をしていると、同時に実行されている別のテストファイルのデータまで消してしまい、原因の分かりにくい失敗（flaky test）を引き起こす。今回は`session`テーブル全体を消す処理が、並行して動いていた別ファイルのログイン状態を巻き込んで壊していた
- **手動テスト（Postman）と自動テスト（Vitest）は役割が違う**。「入力パターンに対して機械的に正しい出力が返るか」（必須項目のチェック・不正な値の拒否など）は自動テストに向いている。パターン数が多く、繰り返し正確に再実行できることに価値があるから。一方「実際にブラウザ・クライアントとして繋いで、意図通りに動くか」（ログイン→Cookie発行→操作、という一連の流れ）は、人間が手を動かして一度確認する価値がある。実際、今回Postmanでの手動確認中に「URLの末尾にコピペで改行が入っていて404になる」という、人間の操作でしか起きない問題を見つけられた
