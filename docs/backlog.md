  で軽く再現を試みたが、SPA遷移（一覧からリンククリック）・フルリロード（URL直打ち）のどちらでも、
  名前欄を書き換えると期待どおり「保存」が活性化し、保存後は再び非活性に戻る、という正常な動作しか
  再現できなかった（`disabled`の条件は`!nameInput.trim() || nameInput.trim() === routine.name || savingName`）。
  そのため、報告された「ずっと非活性」の状態を再現する具体的な手順（使用ブラウザ・OS、日本語入力
  （IME変換）を使っているか、種目の追加/削除/並び替えなど他の操作を挟んだ直後かどうか、等）が
  まだ特定できていない。次に着手する際は、まず再現条件をユーザーから聞き取るところから始める
  - 一応の見立て：`watch(routine, (r) => { if (r) nameInput.value = r.name })`はrefがオブジェクトを
    保持する場合Vueが暗黙にdeep watchするため、種目の追加・削除・並び替え（`routine.value.exercises`の
    書き換え）のたびにも発火しうる。名前を編集した直後にこれらの操作を挟むと`nameInput`が
    `routine.name`へ巻き戻される可能性があるが、これも未検証の仮説に過ぎない

## 技術的負債

- **`prisma`（CLI, devDependencies）の依存に脆弱性**：`@prisma/config`経由で`deepmerge-ts`にhigh脆弱性
  あり（2026-09時点）。`@prisma/client`（実行時に使う方）はこの依存を持たず、`prisma`CLIも開発時にしか
  使わないため実害は低いと判断し対応保留。修正には`prisma@6.12.0`への破壊的ダウングレードが必要な
  ため、Prisma側のアップデートで解消されるのを待つ（`npm audit`で定期的に状況確認）
- **`GET /workouts`が日付範囲での絞り込みに未対応**：常に自分の全workoutを返す（Issue9実装時点）。
  ②ホーム画面のカレンダーは当面この全件取得結果をクライアント側で表示中の月だけ使う形で凌いでいる
  （APIへのリクエスト自体は絞り込んでいない）。記録件数が増えるとレスポンスサイズ・取得時間が
  伸び続ける設計のため、いずれ`performedAt`の範囲指定クエリパラメータをAPI側に追加する必要がある
  - **再検討のタイミング**：実際に一覧取得が重いと感じるようになったタイミング。それまでは
    件数が少なく実害が出にくいため、無理に先取りで実装しない

  - b) 文言を「削除」ではなく状況に応じて変える（例：空なら「この記録をやめる」等、seedのworkout
    自体を消す操作であることが伝わる言い方にする）
  - c) 根本的に、③開始時点で空のworkoutを即作成する設計自体を見直す（「UI改善アイデア」の
    「③種目を1つも追加していないと②に『種目未登録』のリンクが残る」項目、a)案と同じ方向）
  関連：「未決定事項」の「③種目を1つも追加していない状態で『今日の記録を完了』を無効化する
  ガードの要否」も同根の問題（合わせて検討するとよさそう）
  - **再検討のタイミング**：③⑥統合後の画面全体の見た目・文言を整えるタイミング
- **③記録作成の「今日の記録を完了」ボタンが、見た目上「ホームへ戻る」（画面上部のリンク）と
  同じ挙動に見える**（ユーザー指摘、2026-09-04、③⑥統合ステップ4のPRで発見）。③は操作のたびに
  即APIへ反映される設計（`docs/spec.md`§3-2脚注参照）のため、実際にはどちらも「保存して戻る」
  という点で同じだが、2つのボタンが並んでいる意図が伝わりにくい。文言・配置・片方への統合などの
  整理を検討する
- **③記録作成の「メモを保存」ボタンも不要かもしれない**（ユーザー指摘、2026-09-04、③⑥統合
  ステップ4のPRで発見）。③はセットの記録・編集・削除がすでに操作のたびに即APIへ反映される設計
  （`docs/spec.md`§3-2脚注参照）なので、メモだけ明示的な保存ボタンを挟むのは一貫性がなく、
  入力しても保存を押し忘れて消える事故にもつながりうる。入力欄からフォーカスが外れたタイミング
  （blur）で自動保存する、といった仕組みへの変更を検討する。上の「今日の記録を完了」/
  「ホームへ戻る」の整理とも関係するため合わせて検討するとよい
- **③記録作成のセット編集も、値を変更したらその場で反映される（自動保存される）ようにしたい**
  （ユーザー指摘、2026-09-04、③⑥統合ステップ4のPRで発見）。現状は編集モードで重量・回数を
  変更したあと明示的に「保存」ボタンを押す必要がある。「メモを保存」ボタンの見直しと同じ方向性
  （明示的な保存ボタンを減らし、変更をその場で反映する）の課題のため、まとめて検討する
  - **再検討のタイミング**：上記2件と合わせて、③の保存まわりのUIを整理するタイミング
