## ドキュメントと実装のズレ

MVP完成後の棚卸しで見つかった、「決めたはずなのに入っていない」もの。判断がブレる原因になる。

- **種目の表示順**：docsでは「使用回数 → `default_sort_order` → 名前順」の3段階だが、実装は
  **2段階**（使用回数 → 名前順）。`default_sort_order`を全件null運用にしたための意図的な省略だが、
  docs側が更新されていない
- **パスワードリセット**：`users`に`password_reset_token` / `password_reset_expires_at`カラムは
  あるが、APIは未実装

## 技術的負債

- **`prisma`（CLI, devDependencies）の依存に脆弱性**：`@prisma/config`経由で`deepmerge-ts`にhigh脆弱性
  あり（2026-09時点）。`@prisma/client`（実行時に使う方）はこの依存を持たず、`prisma`CLIも開発時にしか
  使わないため実害は低いと判断し対応保留。修正には`prisma@6.12.0`への破壊的ダウングレードが必要な
  ため、Prisma側のアップデートで解消されるのを待つ（`npm audit`で定期的に状況確認）
- **`GET /workouts`が日付範囲での絞り込みに未対応**：常に自分の全workoutを返す（Issue9実装時点）。
  ②ホーム画面のカレンダーは当面この全件取得結果をクライアント側で表示中の月だけ使う形で凌いでいる
  （APIへのリクエスト自体は絞り込んでいない）。記録件数が増えるとレスポンスサイズ・取得時間が
  伸び続ける設計のため、いずれ`performedAt`の範囲指定クエリパラメータをAPI側に追加する必要がある
  - **再検討のタイミング**：実際に一覧取得が重いと感じるようになったタイミング。それまでは
    件数が少なく実害が出にくいため、無理に先取りで実装しない

## UI改善アイデア

- ⑥記録詳細の詳細UI
- セット入力画面の詳細UI（数字入力の方式、＋セット追加のインタラクション、自重トグル）
- セット記録画面：同じ種目で複数セットを連続して行う際、1セットごとに「記録」ボタンを押す方式に
  している（Issue10実装時点）。ジムで実際に使う場面では、複数セット分をまとめて入力してから
  一括登録できた方が手間が少ない可能性があるため、入力方式の改善を今後の課題として検討する
  - **再検討のタイミング**：実際に使ってみて「1セットごとの記録が手間」という体感が積み重なった
    タイミング。それまでは動作の分かりやすさ（都度保存され消えない）を優先し、無理に先取りしない
- ②ホームの「＋今日の記録を始める」ボタンの文言を「＋今日の記録をつける」に変更する案（Issue10の
  レビューで出た指摘）。優先度が低いため見送り、まとめて見直すタイミングで対応する
- ④「もっと見る」をアイコン付きの開閉ボタンにする等の見た目の装飾。優先度が低いため見送り、まとめて
  見た目を整えるタイミングで対応する
- ③のセット記録画面から④種目選択へ直接戻れるリンクを追加する案。「この種目の入力を終える」→
  「＋種目を追加」の2手順で代替可能なため優先度は低いが、動線として欲しくなったら追加する
- ③「今日の記録を完了」を押したときに確認を挟む案（元のIssue10には無かったが、レビューで「押しても
  反応が無いように見える」という指摘から検討したアイデア）。`feat/workout-recording`ブランチでは
  `window.confirm()`を使ったところ、ブラウザが「このページに追加のダイアログを表示させない」を
  自動的に有効化すると以後`confirm()`が常に`false`を返し、ボタンが完全に無反応に見える不具合を
  実機で確認した。**今後この手の確認UIを作るときは`window.confirm()`を避け、画面内の2段階確認
  （キャンセル／実行ボタン）にする**、という学びだけ残しておく（実装例は同ブランチ参照）

## 未決定事項

- **`exercises.default_sort_order`の運用**：当面すべて`null`で運用し、値を設定する手段（管理API・
  シードスクリプトいずれも）は用意しない（Issue5で検討）。結果、MVP期間中は実質「使用回数→名前順」の
  2段階ソートとして機能する。運営（自分）が公式種目を追加する際に「誰が・どう定番順を設定するか」の
  運用ごと決める必要があり、専用の管理APIを作るなら「運営かどうか」を区別する認可の概念（Userにrole
  相当のフィールド等）を新設するコストも伴う。値が最後まで使われないなら、カラム自体を削除する
  選択肢もある
  - **再検討のタイミング**：公式種目のシード投入・追加を実際に行うタイミング（種目データをある程度
    まとめて用意する必要が出た時）。それまでは判断材料（実際に定番順を固定表示したいニーズが本当に
    あるか）が揃わないため、無理に今結論を出さない
- **`routine_exercises`が目安のセット数・重量・回数を持たない**（Issue7で検討）。実際の重量・回数は
  ルーティンから展開した後も`workout_sets`側で毎回手入力する前提（セットごとに値が異なる点は
  `workout_sets`が既にセット単位で独立した行を持つため対応済み）。ルーティンに目安値を持たせて
  入力の手間を減らす拡張は今回のスコープ外として見送った
  - **再検討のタイミング**：Issue11（フロント：ルーティン一覧・編集）〜Issue10（記録作成）の画面実装後。
    実際に「毎回同じ重量・回数を打ち直すのが面倒」という体感が出てから、目安値を持たせる価値を判断する
- **過去日からの記録作成**：③記録作成の入口を「今日」固定にするか、カレンダーで選択した過去日からも
  記録作成を開始できるようにするか。Issue10では「今日」固定として実装（②ホームの「＋今日の記録を
  始める」のみが入口）。過去日からの記録作成対応は引き続き未着手
- **②ホームのカレンダーで日付を選択したときの挙動**：現状は選択してもその日の記録作成には連動しない
  （③の入口は「＋今日の記録を始める」のみ、常に今日固定）。カレンダーで過去日を選ぶとその日の記録
  作成画面が開き、今日の日付を選ぶと今日の記録作成画面が開く、という「日付選択がそのまま記録作成の
  トリガーになる」設計への変更を今後検討する（上の「過去日からの記録作成」とセットで検討する事項）
  - Issue10実装時点では、③の画面設計自体が「今日固定」を前提に作られている（`useWorkoutSession`が
    performedAtを引数に取る形にはなっているため、日付を渡す口自体は用意済み）。過去日対応をやる場合は
    ③の入口設計・ホーム側のUI（カレンダー選択→遷移の導線）を合わせて見直す必要があり、範囲が
    1つのIssueとしてはやや大きいため、Issue10のスコープからは切り離した
  - **再検討のタイミング**：Issue10がひと段落し、次にどのIssueへ進むか検討するタイミング
- **③種目を1つも追加していない状態で「今日の記録を完了」を無効化するガードの要否**。データの意味的には
  空のworkoutが作られてしまう点が気になるが、元のIssue10の完了条件には含まれていないため今回は判断を
  保留する
  - **再検討のタイミング**：空のworkoutが実際に増えて困る場面が出たとき
- **Phase2以降の未着手画面**：グループ関連画面（作成・招待・メンバー一覧・削除）、通知一覧画面、
  ランキング画面、「イチオシこだわり共有」投稿・一覧画面。設計の方向性は
  [concept.md](./concept.md)・[schema.md](./schema.md)に記載済みだが、画面単位の詳細設計は未着手
  - **再検討のタイミング**：MVPがひと段落し、Phase2に着手するタイミング
